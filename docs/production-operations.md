# POSH Inquiry Navigator operations

## Customer activation and renewal

1. Confirm the agreed plan, fee, named account and validity dates outside Navigator. Do not ask for case records, OTPs or passwords. Supply scope and refund/support terms before purchase; never describe a renewal enquiry as confirmed access.
2. Create and confirm the account through the authorised identity dashboard. Only the designated owner/operator assigns access. Use an administrative UUID for purchase verification, never a complaint or payment reference containing case details.
3. Verify the assigned plan, inclusive start and exclusive end in IST. Ask the customer to use email-code sign-in, check the plan and open a fresh workspace. Knowledge-only plans do not include inquiry access. A password session needs the configured additional verification.
4. For renewal, verify payment and dates independently, assign agreed access, then ask the customer to check access again. Keep an existing inquiry tab open while renewing. Never revoke a real customer for testing.

## First-session and case custody

Explain the tool's role: procedural choices, editable drafts and local dates; the Committee authorises service, findings and recommendations. Work with codes only. Keep signed records, originals and identities in the institution's secure system. A document download does not serve a notice or complete a milestone.

Save and verify a recovery file. In supported browsers, the user can explicitly enable updates to that chosen file every fifteen seconds while the tab is open. The last unsaved changes remain at risk until a read-back succeeds. File permission loss, external edits, restore, restart and scenario switching disconnect automatic updates. No file handle, case progress or draft is persisted in browser storage or sent to the account server. Unsupported browsers retain download-and-check recovery. Restore preview is mandatory; imported history is untrusted.

## Support and incidents

Support contact: training@thecosmicenergizers.com. Request account email, approximate time, browser/version and a redacted description. Never request passwords, email codes, case files, evidence or recovery JSON. Obtain specific consent before sharing a redacted diagnostic with another provider. No guaranteed response time or 24-hour cover is advertised.

During account outages: keep inquiry tabs open, save and verify recovery, retry access, and use a separate account tab. Never refresh unfinished work as a first step. If a suspected account compromise occurs, the owner checks account logs and revokes the relevant identity sessions through the authorised provider, reviews plan changes and follows applicable notification duties. Do not change case dates or records to hide an incident.

## Release and rollback

Before publication: build/hash verification; timeline/document tests; OTP, paid lifecycle, recovery, failure injection, keyboard and 320px checks. Review only intended source changes; exclude credentials, customer data and QA exports. Record commit, tree and deployment IDs. Do not grant actual customer access for a synthetic test.

Render has auto-deploy off. Trigger exactly one tested commit in the separate Navigator workspace; wait for LIVE, then check health version, public hashes, protected-asset denials, security headers and startup errors. Use a new test tab; preserve customer tabs and files. Keep the prior known-good commit and source archive. For rollback select that exact prior commit, verify current environment compatibility, trigger and confirm LIVE plus health/version. No database migration is included in 5.8; rolling back the app does not undo plan changes or locally downloaded files.

## Periodic review

Before each release and material legal change: check authoritative Act/Rules, applicable sector directions, template safeguards and current appellate/criminal-law instruments. After authentication or database changes: run identity security advisors, review RLS and owner RPC guards, and negative-test customer permissions. Record unresolved findings honestly. Free hosting may cold-start; no uptime SLA is claimed. Leaked-password screening currently requires paid Supabase Pro, so email OTP remains the primary free login. Independent legal sign-off, assistive-technology user testing and penetration testing remain external validation tasks, not completed by this internal checklist.
